**Status: WAITING ON EXTERNAL BUSINESS INPUTS (2026-08-04).**

Phases A and B are built, proven against a real host, and **frozen**. Phase C is
**frozen before implementation** — see the scope review below.

**M015 is complete only when Atlas deploys and operates one real customer website
on a public domain.** That is still false, and what blocks it is not code:

2. **A first customer** — internal counts; Teqtronix or Oskar is enough

**Until then: no monitoring, alerting, dashboards or operational features.** A
monitor watching a site nobody can reach measures nothing, and a green dashboard

Work resumes when Atlas is connected to a real customer. The roadmap gets a
review before M016 begins.

Ranked second in [`BUSINESS_ROADMAP.md`](BUSINESS_ROADMAP.md). Governed by
[`SHIP_RULE.md`](SHIP_RULE.md). Follows the architectural discipline of M013
(Media) and M014 (Opportunity), and **does not redesign either**.

## Goal

**Atlas builds, deploys and maintains a real website for a real paying customer,
on a real domain, without Ayoub or his team touching a build tool.**

Not a site builder. Not a template gallery. The narrowest thing that turns a
signed customer into a live URL and keeps it live.

M014 finds businesses whose sites are missing, unreachable, unusable on a phone,
or invisible to search engines, and proposes fixing exactly that.
**M015 is the fulfilment of the offer M014 already makes** — which is what keeps
its scope honest. Anything that does not help deliver that offer is out.

## Success criteria

Numbers, not a demo. The milestone is done when these are true and measured.

### The one that decides everything

**At least one website built by Atlas is deployed on a real domain and paid for
by a real customer.** Under SHIP-1 nothing else in this list matters if this one
is false.

### The self-consistency criterion

**Every site Atlas deploys scores zero findings from Atlas's own M014 website
detector.**

This is free — the detector already exists, needs no credentials, and inspects
exactly the defects the offer promises to fix. It would be indefensible to sell
a business a fix for a missing `<meta viewport>` and ship them a site without
one.

Run as an automated gate before deployment, not as a manual check. It is the
enforcement mechanism for the output contract below.

### The reproducibility criterion

**Atlas must be able to rebuild and redeploy any site entirely from Business
memory, with no manual reconstruction.**

Delete the build output, delete the working directory, and the site rebuilds
from what Atlas durably knows about that company — the Site content, its
provenance, and the `Business` record — and redeploys to the same place.

This is the same rule M013 applies to renders, and it is what makes a site an
*asset Atlas owns* rather than a thing that happened once. The failure it
prevents: a customer asks for a change eighteen months later, and the site can
only be edited by whoever still has the folder. A factory whose output cannot be
rebuilt is a consultancy with extra steps.

Two consequences worth naming now, because they are cheap to design in and
expensive to retrofit:

- **Nothing enters a site that is not in the durable record.** No content pasted
  into a prompt, no image dropped into a folder, no hand-edited HTML. If it is on
  the site, Atlas can produce it again from the database.
- **Rendering must be deterministic.** Same content in, same bytes out — so no
  build timestamps, no generated ids, no unordered iteration in the output. That
  is what lets "rebuilt correctly" be *verified by comparing fingerprints* rather
  than by a person looking at two pages side by side.

Tested by rebuilding from a clean checkout against the database alone and
comparing the artifact fingerprint.

### Operational

| Criterion | Measure |
|---|---|
| Time to live | Hours from "customer says yes" to verified live URL, against the current manual baseline |
| Deploy verification | Every deployment confirmed live and healthy by a fetch, not by the deploy tool's exit code |
| Rollback | A bad deployment reverted to the previous version and verified, in one step |
| Redeploy | A content change republished without rebuilding by hand |
| Provenance | Every deployment records what produced it — content version, theme, generator, host, timestamp |
| Timeline | Every build, deploy, rollback and check appears on the business's `BusinessEvent` timeline |

### Manual work eliminated

Measured against the current process: how many minutes of Ayoub's or his team's
time a site costs end to end, before and after. This is SHIP-1 priority 2 and
the criterion most likely to be quietly skipped, so it gets a number.

## Scope

Three phases, ordered so the **riskiest and most blocking part ships first**.
Deployment is the hard dependency and the genuine unknown; generation is the
part we can already estimate. Doing generation first would mean discovering the
deployment problems last, with a customer waiting.

### Phase A — Deployment spine (the blocker) — **FROZEN, PROVEN 2026-08-04**

> All six criteria demonstrated end to end against a real remote host. See
> `docs/WEBSITE_FACTORY.md` and `infra/phase_a_proof.py`. Frozen: no further
> architectural change unless running Phase B against it reveals a real problem.

Take an **authored** site — HTML written by hand, no generation — and put it
live, verifiably, with rollback.

- A `site.deploy` capability designed against both Cloudflare Pages and Hetzner,
  so the host is disposable exactly as media providers and outreach channels are
- Domain and TLS wired
- Post-deploy verification by fetching the live URL, not by trusting the tool
- Rollback to the previous version
- Deployment provenance recorded
- `factory="website"` events on the business timeline

**Phase A alone already eliminates manual work**, and can deliver for a customer
Ayoub sold by hand. That is deliberate: it is the smallest thing that reaches the
real world.

### Phase B — Generation — **FROZEN 2026-08-04**

> Implemented, and a generated site deployed to a real host with the gate passing
> on zero findings. Frozen: no further architectural change unless real use
> reveals a real problem.

- A **Site content model**, independent of rendering — business details,
  services, hours, location, contact. One source, many renditions, exactly as
  M013 separates Script/Scene from Rendition.
- One theme family, one vertical
- Rendering that satisfies the output contract below
- Generation seeded by the `Business` record M014 already holds, plus content the
  operator or customer supplies
- **No fabricated business facts** (see *Invariants*)
- The M014 detector gate

### Phase C — Keep it live — **FROZEN BEFORE IMPLEMENTATION 2026-08-04**

> Reviewed and deliberately not built. See the scope review below. Unfreezes when
> a real customer site is live on a public domain — not before.

- Uptime and health checks on deployed sites
- Content change → redeploy
- Failure surfaced on the business timeline and to the operator

### Does Phase C belong in M015?

**Split verdict, and the split follows the offer.** Ayoub chose *build +
recurring hosting*, and that decides it: a recurring fee for hosting is a fee for
**the site staying up**. Charging it monthly while never checking is not a
product.

**Stays in M015** — the smallest version of the recurring deliverable:

- A scheduled check of each live site, using the existing `check_live()`
- Result on the business timeline, which already happens
- Failure visible to the operator

This is small. `check_live()` exists, the scheduler exists, the events exist. It
is the deliverable behind the fee, and without it the recurring half of the offer
is a line on an invoice.

**Moves out of M015** — everything that makes it a monitoring *product*:

- Alerting channels, escalation, on-call routing
- Status pages, SLA reporting, uptime history dashboards
- Multi-region or synthetic checks, performance budgets, regression alerts

Each is a reasonable thing to want and none has a user on day one. They belong to

"operating what the other factories shipped". Building them here is how a website
milestone becomes a monitoring platform.

### Recommended order, and it is not Phase C first

Under SHIP-1 the next work is **not** Phase C. A monitor watching a site nobody
can reach measures nothing, and building it before a public site exists is
architecture ahead of revenue — the exact failure the rule was written for.

1. **Resolve the hosting decision and put one real site live on a real domain.**
   This is criterion #1. Blocked on Ayoub, not on code.
2. **Then Phase C (reduced),** because by then there is something whose staying
   up a customer is paying for.
3. Everything else in the list above → a later milestone, when a customer's
   absence is costing something.

**Recommendation: hold Phase C until step 1 lands.** If the hosting decision is
going to take time, Phase C reduced is a reasonable thing to build in the gap —
it is small and it is genuinely part of the offer. It is just not the thing that
moves the milestone.

## Explicit non-goals

Each is a decision, not an oversight. Several are things a website product
"obviously" needs, and building them is how this milestone becomes a platform
project instead of a revenue one.

**Not building:**

- **A CMS or customer-facing editor.** Content changes go through Atlas. A
  self-serve editor is a product in its own right and has no user on day one.
- **A multi-tenant hosting platform.** Atlas deploys sites; it does not become a
  hosting company with plans, quotas and dashboards.
- **Billing, subscriptions or invoicing.** Ayoub invoices. Automating that
  before there is recurring revenue to automate is backwards.
- **E-commerce, carts, payments on customer sites.**
- **A template marketplace or theme gallery.** One theme family, one vertical.
- **Arbitrary framework support.** The output contract permits any stack that
  meets it — static, Astro, server-rendered — but M015 implements **one**.
  Supporting whichever framework a customer names is a platform feature with no
  customer asking for it. The contract keeps the door open; this milestone does
  not walk through it.
- **Domain registration and purchase automation.** Pointing DNS is manual for the
  first sites; automating it needs a registrar API, payment, and a real volume
  of sites to justify it.
- **Brand identity generation** — logos, colour systems, illustration.
- **Multi-language sites.**
- **Analytics infrastructure.** A snippet if the customer wants one; not a
  product.
- **Any redesign of M014.** It is frozen. M015 *uses* `Business`,
  `BusinessEvent` and `business_id`; it does not reshape them.
- **A generic "Deployment Factory."** Deployment is built thin, inside the
  factory that needs it, per SHIP-1. It is extracted when a second factory needs
  it — not before.
- **Multi-worker scheduling / distributed execution.** Still frozen from M013.

## Invariants

Carried from M013 and M014 unchanged. Named here so M015 is judged against them.

| Invariant | Origin | What it forbids here |
|---|---|---|
| Content independent from rendering | M013 | Theme or HTML details on the Site content model |
| Providers disposable, capability-based | M013 | The kernel knowing which host deployed a site |
| Everything reproducible | M013 | A deployment with no record of what produced it; **any site content that exists only outside the database** |
| Approval on outcomes, fingerprint-bound | M013/M014 | Publishing something a human did not see; an approval surviving an edit |
| One customer entity, immutable ids | M014 | A `WebsiteClient`; anything but `business_id` |
| Every factory writes the shared timeline | M014 | A website history separate from the company's |

### Atlas owns Business memory, not the hosting

**Every deployment must be reproducible independently of the hosting provider.
Moving a customer between providers is a normal deployment, never a migration
project.**

Concretely, this decides four things in Phase A rather than being a sentiment:

- **Atlas holds the artifact.** The built bundle lives in Atlas's own durable
  record. A provider is handed a copy; it is never the place the site exists.
- **Atlas holds the deployment state.** Which version is live, and where, is
  Atlas's record — not something read back from a provider's API. A provider
  that loses its history, changes its API or ends the account cannot take the
  answer with it.
- **Rollback comes from Atlas's artifacts**, not the provider's version list.
  Otherwise rollback silently becomes a provider feature and stops working the
  moment the provider is swapped.
- **Changing host is publish + promote to a different target.** No export step,
  no reconstruction, no "migration". If moving a customer needs a plan, the
  abstraction has already failed.

The test is blunt: deploy to one target, then deploy the *same build* to another
and promote it, and the second must be a normal operation producing an identical
artifact.

### New invariant this milestone introduces

**No fabricated business facts on a published site.**

M014's rule is that Atlas may not make a claim about a business it cannot
substantiate. Publishing *as* that business is strictly worse: invented opening
hours, a made-up service list or a plausible-sounding address are wrong in the
customer's own voice, on their own domain, and they carry the consequences.

Every factual field on a rendered site traces to something the business or the
operator supplied, or it does not appear. Prose may be written; **facts may not
be invented.** This is an enforced invariant, not a prompt instruction — the same
standing as "no finding without evidence".

## Output contract — a property, not a technology

**Requirement: SEO-first, detector-clean output.** Static HTML, Astro, or any
server-rendered or pre-rendered stack is acceptable. **Client-side-only rendering
is not.**

Stated as a property rather than a choice on purpose, and it is the same
discipline as capability-based providers: the kernel asks for `video.generate`
and never names Wan or Seedance, so here the requirement names what the output
must *be*, not what produces it. A technology named in this document would
outlive the reason it was named.

The contract, enforced by the detector gate above:

| Must | Why |
|---|---|
| Meaningful HTML in the served response | What the detector reads is what search engines read. A homepage that is an empty div until JavaScript runs fails both. |
| A `<title>`, meta description, `<h1>` and viewport in the served markup | These are the defects being sold against |
| Structured business data in the document | Hours and location appearing in search results is part of the offer |
| Fast first response | "Slow homepage" is a finding on the proposal |

Anything satisfying that is permitted. The choice is made per site if it ever
needs to vary, and the gate — not a rule in a document — is what stops a
regression, because a stack that stops meeting the contract fails the build.

**One consequence to be explicit about:** CLAUDE.md's Next.js decision governs
**the Atlas application**, not customer sites. Different product, different
constraints. Worth stating so the two are never conflated.

## Deployment abstraction — decide the host later

**Build the abstraction; do not pick the host.** `site.deploy` must be capable of
serving **both Cloudflare Pages and Hetzner**, and Atlas chooses at deploy time
rather than the choice being baked into the code.

This is not speculative generality — it is the difference between an interface
and a wrapper, and getting it wrong is only visible when the second adapter
arrives. The two hosts work differently enough to be a real test:

| | Cloudflare Pages | Hetzner |
|---|---|---|
| Publish | Upload a bundle, get an immutable deployment | Copy a versioned directory to the server |
| Activate | Promote a deployment id | Swap a symlink, reload the web server |
| Rollback | Promote the previous deployment id | Swap the symlink back |
| TLS | Automatic | Caddy / ACME |
| DNS | Cloudflare | External |

**The shape that fits both: publish a versioned artifact, then promote it.** An
interface phrased as "copy these files to this path" would encode Hetzner's model
and Cloudflare would not fit; one phrased as "upload and get a deployment id"
would encode Cloudflare's and Hetzner would not. Publish-then-promote is what
they have in common, and it is also what makes rollback a first-class operation
rather than a redeploy of older content.

Practically, for Phase A:

- The capability interface, designed against both hosts' requirements
- **One adapter implemented**, plus a second thin enough to prove the interface
  does not leak the first host's assumptions. A single adapter cannot
  demonstrate that, and an interface validated only in prose is validated by
  nobody.
- Selection by registration and policy, exactly as media providers resolve —
  so "which host" becomes configuration rather than a code change

## How this follows SHIP-1

| SHIP-1 | M015 |
|---|---|
| **Revenue** | Directly sellable. A website is the most immediately saleable output of any factory on the roadmap, and the success criterion is a paid deployment rather than a working demo. |
| **Manual work eliminated** | Build-and-deploy stops being human time. Measured, not asserted. |
| **Products shipped** | Each site is a shipped product on a real domain. |
| **Smallest thing that generalises** | One vertical, one theme, one host, one stack. Deployment built thin **inside** the factory that needs it rather than as a "Deployment Factory" — extracted only when a second factory needs it. |
| **Real world sooner** | Phase A ships before generation exists, so something is live and useful early. |
| **Not an architecture project** | The non-goals list is mostly platform features a website product "obviously" needs. Each is refused because none has a customer on day one. |
| **Compounding rather than one-off** | Rebuild-from-memory is what makes each site an asset Atlas owns and can maintain, instead of a delivery that has to be redone by hand. A factory whose output cannot be rebuilt is a consultancy with extra steps. |

**What it sets up.** Website Factory closes the loop with M014 — Opportunity
finds businesses with broken or missing sites, Website delivers the fix — and it
buys the deployment spine that AI SaaS will need later. That is leverage bought
by shipping, which is the only kind SHIP-1 permits.
