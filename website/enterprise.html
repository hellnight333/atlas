Atlas for teams

Multi-tenant governance is built and working. One caveat matters more than the rest, and it is stated first.

The kernel API has no authentication

Atlas binds to localhost and assumes one trusted operator on the machine. The organization and permission system governs actions inside Atlas — it is not a network authentication layer. Do not expose Atlas to a network you do not control. A shared team deployment is not supported in this release.

What is implemented

Organizations and roles

Creating an organization seeds seven built-in roles, from owner to viewer. Custom roles resolve through identical code, so they are not second-class.

Permissions you can explain

Every granted permission comes back with the role and membership that produced it — the same data support and the UI both see, so answers never disagree.

Policies that inherit

Organization → Workspace → Project → Object

A narrower scope overrides a broader one, key by key. Lock a key and no narrower scope can override it — that is the enforcement mechanism, not a suggestion.

Membership with expiry

Temporary access grants nothing after its expiry. There is no grace period.

Append-only audit

Logins, permission changes, policy changes, worker assignment, publishing, deletion and exports. There is no update or delete path for an audit record anywhere in the kernel, and re-inserting a modified one is a no-op.
