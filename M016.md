# M016 — Amazon Factory (proposed)

**Status: PROPOSED. Awaiting review. No implementation started.**

Ranked first in [`ROADMAP_REVIEW_2026-08.md`](ROADMAP_REVIEW_2026-08.md).
Governed by [`SHIP_RULE.md`](SHIP_RULE.md). Follows the discipline of M013, M014
and M015, and **redesigns none of them**.

---

## Goal

**Measurably improve the performance of Oskar's live Amazon listings, using
evidence, and prove the lift against a real baseline.**

Not a listing tool. Not a seller dashboard. The narrowest thing that turns
Atlas's analysis into more revenue on a catalogue that is already selling.

---

## Why this one, and why now

Three factories are frozen on external inputs. **This milestone is chosen partly
because it cannot be.** Its customer already exists and already pays, its data is
public, and its first deliverable needs one input Ayoub already has: a list of
ASINs.

| | |
|---|---|
| **Customer** | Oskar Phones and Teqtronix — Ayoub's own, selling on Amazon UAE and KSA today |
| **Revenue** | A lift on GMV that already exists. No acquisition, no close rate, measurable against a live baseline |
| **Credentials needed for the first deliverable** | **None.** Listing pages are public |

---

## The governing constraint

> **If it can freeze on an external input, it is out of the first deliverable.**

From the roadmap review. SP-API, Seller Central automation, ad data and inventory
feeds are all *desirable* and all *capable of blocking*, so none of them are on
the critical path. They are Phase 2 and beyond, entered only once Phase 1 has
produced a measured result.

---

## Success criteria

### The one that decides everything

**A measured before/after on real ASINs.** Not "listings improved" — a number,
against a baseline captured before anything changed. If the lift is not there,
that is the most valuable thing this milestone can produce, and producing it in
days rather than months is the point.

### Supporting

| Criterion | Measure |
|---|---|
| Evidence | Every recommendation cites what was observed on which listing, when — the M014 rule, unchanged |
| Confidence | Every finding carries a justified confidence, so weak signals cannot pile up into a confident recommendation |
| Baseline | Captured and stored **before** any change, or the lift cannot be claimed |
| Manual work | Hours of catalogue analysis replaced, measured against how long it takes Ayoub's team today |
| Reproducibility | Any recommendation can be re-derived from Atlas's record |

---

## Scope — Phase 1 only

Phase 1 is the whole of this proposal. Later phases are named so the shape is
clear, and are **not** approved here.

### Phase 1 — Evidenced listing analysis (no credentials)

- Ingest a list of ASINs Ayoub supplies
- Fetch the public listing for each, and for named competitors
- **Detectors producing evidenced findings** — reusing M014's `Finding`,
  `Evidence`, confidence and detector-registry machinery unchanged. A listing is
  a surface to inspect, exactly as a website is.
  - Title: length, keyword placement, model/variant clarity
  - Bullets: count, length, benefit vs specification balance
  - Images: count, presence of the sizes Amazon rewards
  - Description / A+ presence
  - Backend keyword gaps against competitor titles
  - Rating and review-count position against the same
- **Baseline capture** per ASIN before anything changes
- Recommendations, ranked, each citing its findings
- Everything on the **shared `BusinessEvent` timeline** under `factory="amazon"`

**Deliberately not in Phase 1:** applying changes. Ayoub applies the top
recommendations by hand — which takes seconds per listing, while *deciding what
they should be* takes hours. The hours are what this eliminates.

### Later phases — named, not approved

- **Phase 2** — apply via SP-API, once access exists
- **Phase 3** — scheduled monitoring and competitor tracking
- **Phase 4** — sell it as a service to other GCC sellers

Phase 4 is where this compounds, and it runs through the Opportunity Factory —
which is the leverage argument the last review made, arriving on schedule rather
than being abandoned.

## Explicit non-goals

- **No SP-API on the critical path.** Approval is slow and would freeze this
  milestone like the last three.
- **No Seller Central automation.** That is the Browser Agent, ranked second.
- **No generic marketplace abstraction.** Amazon only. Noon, eBay and Shopify are
  a second implementation looking for a first user.
- **No inventory forecasting, pricing or repricing.** Different problem, real
  money, deserves its own milestone.
- **No advertising management.** Live ad spend is not a place for a first version.
- **No dashboards or monitoring.** The M015 lesson: operational features need
  something in operation.
- **No image generation in Phase 1.** Media is frozen on a GPU worker; depending
  on it would import that freeze.
- **No redesign of M013–M015.** M016 *uses* `Business`, `BusinessEvent`,
  `Finding`, `Evidence` and the detector registry. It reshapes none of them.

## Invariants

Carried unchanged. M016 is judged against them.

| Invariant | Origin | What it forbids here |
|---|---|---|
| No claim without evidence | M014 | A recommendation not citing what was observed |
| Confidence justified by how it was observed | M014 | An invented number that looks like rigour |
| One customer entity, immutable ids | M014 | An `AmazonSeller`; anything but `business_id` |
| Every factory writes the shared timeline | M014 | An Amazon history separate from the company's |
| Everything reproducible | M013 | A recommendation that cannot be re-derived from the record |
| Content independent from rendering | M013 | Findings that only make sense as a report |

### The one M016 adds

**A baseline captured after a change is not a baseline.**

The whole milestone rests on a before/after. If the "before" is measured once the
listing has already moved, the number is decoration — and it will be a flattering
one, which is worse. Baseline capture happens before any recommendation is
applied, is stored immutably, and a comparison against a baseline recorded later
than the change is refused rather than reported.

| SHIP-1 | M016 |
|---|---|
| **Revenue** | Lifts GMV that already exists. The success criterion is a measured number, not a demo. |
| **Manual work eliminated** | Catalogue analysis is hours per listing today; applying a decided change is seconds. This takes the hours. |
