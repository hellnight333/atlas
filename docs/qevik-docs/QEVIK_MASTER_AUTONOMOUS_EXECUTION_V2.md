# 15. QEVIK AI CONTROL PLANE — THE OPERATING SYSTEM FOR THE WHOLE DEVELOPMENT LOOP

The Qevik application must ultimately become the control plane for the complete Qevik development and execution process.

This is not a cosmetic dashboard.

It must preserve the same disciplined loop currently performed manually between ChatGPT and Claude:

USER REQUEST
→ CONTEXT / HISTORY
→ ARCHITECTURAL ANALYSIS
→ PLAN
→ APPROVAL / INPUT REQUEST
→ AGENT EXECUTION
→ TESTS
→ REPORT
→ GIT COMMIT
→ GIT PUSH
→ CONTINUE

The system must make this loop persistent, inspectable, resumable and provider-independent.

## 15.1 Persistent project memory

Every development session must be persisted.

Persist at minimum:

- complete user/agent conversation history
- system-generated plans
- revisions of plans
- decisions
- blockers
- requested credentials/configuration
- submitted credentials/configuration metadata
- agent actions
- tool calls
- files changed
- tests executed
- test results
- commits
- pushes
- reports
- errors
- warnings
- approvals
- rejected plans
- phase transitions
- discovered architectural decisions
- discovered future work
- generated roadmap amendments

Do not rely on chat history in the browser.

The database must be the source of truth.

Every session must be reopenable months later with enough context for another agent to continue without reconstructing the history manually.

## 15.2 Project/session timeline

Create a chronological timeline for each project.

Example:

P2.4
→ plan created
→ user approved
→ Claude execution started
→ 14 files changed
→ 2261 tests passed
→ blocker discovered
→ blocker converted to user action
→ commit created
→ pushed to GitHub
→ report stored
→ P2.5 started

Every event must have:

- timestamp
- actor
- model/provider
- action
- status
- relevant phase
- git SHA where applicable
- links to artifacts/reports where applicable

The user must be able to open any event and inspect it.

## 15.3 Reports are first-class artifacts

Every execution report must be automatically saved.

Do not only display it in chat.

Store:

- Markdown report
- structured JSON summary
- phase
- task
- git SHA
- changed files
- tests
- blockers
- decisions
- next actions
- timestamps
- agent/provider

Also write reports into the repository, for example:

  P1.2/
  P1.3/
  P2.1/
  ...

The database and Git repository must agree on report identity and revision.

Never overwrite a previous report silently.

Use immutable report revisions.

## 15.4 Chat must behave like a serious AI engineering workspace

The main interface should feel closer to an engineering command center than a generic chatbot.

The user should be able to write:

13. commit/push if authorized
14. continue to the next task

The planning response should be persistent and versioned.

Do not make the user copy/paste plans between systems.

# ADDENDUM — QEVIK 24/7 MISSION CONTROL, AGENT UX & COST INTELLIGENCE

This addendum is mandatory. It extends the master execution specification and takes precedence wherever the earlier document is silent about persistent execution, agent UX, model selection, cost tracking, or recovery.

## A. Core principle: the website is NOT the runtime

`app.qevik.ai` is a control plane and observation surface.

Closing the browser, closing the tab, losing the browser connection, or navigating away MUST NOT stop a queued/running agent job.

The execution architecture MUST be:

```text
app.qevik.ai
      │
      ▼
Control API
      │
      ▼
Persistent Job Store
      │
      ▼
Queue / Orchestrator
      │
      ├── Planner Agent
      ├── Claude Agent
      ├── Codex Agent
      ├── Qwen Agent
      ├── DeepSeek Agent
      └── Other providers
      │
      ▼
Worker / Agent Runtime
      │
      ├── Git
      ├── tests
      ├── lint/type checks
      ├── reports
      └── roadmap state
```

A browser request MUST NOT hold open the execution lifecycle.

Every execution must survive:
- browser close
- tab close
- refresh
- network interruption
- UI crash
- API request timeout
- worker restart
- server restart

Jobs must be persisted and recoverable.

## B. Durable job lifecycle

Every plan/task/agent execution must have an observable state.

`DRAFT`
→ `PLANNING`
→ `PLANNED`
→ `QUEUED`

→ `PROCESSING`
→ `WAITING_FOR_INPUT`
→ `WAITING_FOR_APPROVAL`
→ `WAITING_FOR_PROVIDER`
→ `RETRY_PENDING`
→ `VERIFYING`
→ `COMPLETED`

Terminal/error states:

`BLOCKED`
`FAILED`
`CANCELLED`
`ABANDONED`

Do not use vague "running" for everything.

Each transition must record:
- timestamp
- actor/agent
- reason
- job id
- phase/task id
- provider/model where applicable

The UI must display the current state and the transition history.
