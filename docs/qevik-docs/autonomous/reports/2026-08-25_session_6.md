# Autonomous session — the operating fabric: scheduler, protocol, budgets

From `a29a68d`, 25 August 2026. Steps 2–4 of the ordering the operator set after
the Munder-Difflin review. Steps 0 and 1 shipped in `a29a68d`.

## Where this started

The Munder-Difflin review named the gap: **orchestration is not intelligence**.
Qevik could plan, approve, execute, publish and report — and had no operations
department. The worker took one queued mission per pass, oldest first, and that
was the whole of its judgement.

The operator's ordering was: live status → agent registry → **scheduler** →
**message protocol** → **budgets** → Postgres claims → CLI backend → tool agents.
This session is the middle three.

## The scheduler

`fabric/scheduler.py` · `SCHEDULER.md`

Five queues. The one that carries the design is the split between the last two:

> `WAITING` resolves by itself. `BLOCKED` never will.

Merged, they produce a queue where half the entries are progressing and half are
dead and nobody can tell which by looking — so the operator either chases things
that were fine or ignores things that were stuck. They are separate queues, and
a test asserts they are not the same queue rather than asserting a happy path.

The order of the checks *is* the policy: blocked, then credential, then
placement, then budget, then waiting, then a chosen window, then the night
window, then ready. Asking "is there capacity" about work that cannot run at all
produces a queue full of things that look imminent.

Four decisions worth naming.

**UNKNOWN cost is neither free nor a wall — and the first version got this
wrong.** It reused the night-window threshold (`EXPENSIVE_UNITS = 50`) as the
affordability test for unpriced work, which blocked every unestimated mission on
the LIST plan (40 units) for ever. "Can we afford this estimate" and "should we
start something nobody priced" are different questions. Two thresholds now:
priced work is refused when its estimate exceeds what remains; unpriced work is
refused only when headroom is below `UNPRICED_NEEDS`, and the reason names the
missing estimate rather than a size. A test pins it against the real LIST
allowance rather than an abstract number.

**A missing credential is BLOCKED, not WAITING.** Nothing resolves it but a
person typing a key, and the reason names the Credential Centre — a reason that
does not say where to fix it is a status, not an action.

**Deferring is a decision, and it is enforced.** `service.defer()` records
`not_before` as an ordinary append-only event; the mission stays *queued*,
because it is still work somebody wants done. Then `claim()` refuses a mission
whose window has not arrived. Without that last part the worker — which takes
the oldest queued mission — would run the night job at eleven in the morning and
the deferral would be a suggestion.

**Oldest-first inside a priority.** Ordering by priority alone starves the
NORMAL mission that has been waiting since Tuesday behind a trickle of newer
NORMAL work.

Durability is shown across a real process boundary: a deferral written by the
test interpreter is read by a `subprocess` that never saw it — with a negative
control proving the same fresh process *would* have run the mission without the
deferral, so the test cannot pass against a scheduler that defers everything.

## The message protocol

`fabric/protocol.py` · `AGENT_PROTOCOL_AND_BUDGETS.md`

Two agents that can talk can talk forever.

**An agent addresses a capability, never an agent.** `needs=Capability.RESEARCH`,
not `to="researcher"`. This is what keeps "agents cannot recruit agents" true
while agents still collaborate: an agent that could name its correspondent could
build a private chain outside the registry — working relationships nobody
declared and no policy covers.

**The cap escalates; it does not truncate.** At the hop limit, the message limit
or the budget, the conversation goes to a person with the whole chain attached.
Silently returning the last message hands the caller a half-finished answer that
reads like a finished one, and the loop — invisible — runs again tomorrow. The
escalation is written *even when the message cap is already full*, because the
cap bounds work, not the record of why the work stopped.

**Cycles are caught by who is still waiting**, not by who has been asked before.
A second question to the same specialist, after the first was answered, is
ordinary work; a rule that called it a loop would block normal collaboration. A
failure counts as an answer, so a legitimate retry is not refused as a cycle.

`REFUSED` (a rule said no, and which) stays distinct from `FAILED` (something
broke). A caller that cannot tell them apart retries against a limit that will
refuse it every time.

## Budgets — and the mistake caught on the way

`fabric/budgets.py`

    TENANT   ⊃   MISSION   ⊃   AGENT   ⊃   CONVERSATION

Checked against **all**, committed to **all**. Checking only the tightest lets a
hundred conversations, each inside its own small budget, empty the tenant's;
checking only the widest lets one of them do it alone; committing scope by scope
leaves the tenant charged for a spend the conversation refused, and that
overcharge is invisible.

**The mistake:** the first version invented `budget.<tenant>` as the tenant
allowance. `credits/` already owns that question — a customer's plan, registered
on this same ledger by `CreditService.assign()`. Two answers to "what may this
customer spend", and the wrong one is always whichever the operator is not
looking at. `Scope.TENANT` now resolves to the credits resource, `policy()`
refuses to define a tenant allowance at all, and a test pins the delegation.

This is the same failure mode as the parallel-maps and second-registry problems
recorded earlier in this project, caught this time before it shipped.

`Unmetered` is deliberately not a `QuotaExhausted`: "you have no allowance
configured" and "your allowance is gone" have opposite remedies, and a caller
that confuses them waits for a window that is never going to reset.

## What is wired

`GET /api/missions/schedule` asks `CreditService.balance()` for the tenant's real
remaining units — `balance()`, not the raw ledger, because it also subtracts
units already reserved and not yet settled. A mission whose plan estimates more
than the tenant can afford is `BLOCKED` before it starts.

`usable_credentials()` asks the same question `resolve()` asks: is the status
outside `UNUSABLE`? A credential somebody typed and nothing verified is exactly
the case where the scheduler would dispatch work that fails at the provider. A
sealed vault yields the **empty set** — not knowing which keys work is not the
same as knowing they all do.

New surfaces: `GET /api/missions/schedule`, `POST /api/missions/{id}/defer`
(requires `EXECUTE` — changing when work runs is an execution decision), and a
**Schedule** page in the console drawing the five queues apart.

## What is not built, stated rather than implied

- **Nothing calls `reserve()` from the worker.** The budget layer is complete
  and tested and the scheduler consults the tenant balance, but per-mission,
  per-agent and per-conversation allowances are not charged at execution time.
- **`Conversation` is not persisted.** It is designed to fold — frozen,
  counters derived from the messages — but no event kind writes it.
- **Provider rate limits** are not a scheduling or protocol input.
- **Multi-worker capacity is not discovered.** `concurrency` is supplied by the
  caller. `PostgresClaims` still refuses to construct unverified, so more than
  one worker is not safe yet — step 5.
- **CLI/coding-agent backend** stays `not ready` in the registry, because Qevik
  has no sandbox and marking it ready would dispatch a filesystem-writing
  process into a worktree and call that isolation — step 6.
