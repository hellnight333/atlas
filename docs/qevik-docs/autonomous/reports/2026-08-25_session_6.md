# Autonomous session — the operating fabric, end to end

From `a29a68d`, 25 August 2026. **Steps 2 through 7** of the ordering the
operator set after the Munder-Difflin review; steps 0 and 1 shipped in
`a29a68d`, steps 2–4 as `aa09e07`, steps 5–7 below.

Two of the remaining steps were listed as `PENDING_INFRASTRUCTURE` and both
blockers had **already lifted** — the host had PostgreSQL 18.6 and bubblewrap
0.11.1 installed, and nobody had re-tested the note. A blocker nobody re-tests
is indistinguishable from a blocker that is still real, and both stop work.

Seven real defects were found. Four of them only surfaced when something was
actually run — against a real database, a real kernel namespace, or the real
registry — and the other three when a neighbouring module was read rather than
assumed. Each is in the section where it was found, and all seven are listed
together at the end.

## Where this started

The Munder-Difflin review named the gap: **orchestration is not intelligence**.
Qevik could plan, approve, execute, publish and report — and had no operations
department. The worker took one queued mission per pass, oldest first, and that
was the whole of its judgement.

The operator's ordering was: live status → agent registry → scheduler →
message protocol → budgets → Postgres claims → CLI backend → tool agents. Steps
0 and 1 shipped last session; this one covers **the remaining six**.

The two defects worth reading first, because neither would have produced an
error: an autocommit connection releases the row lock *before* the claim is
recorded, so two workers would have claimed one mission silently; and `browser`
declared REVERSIBLE while a browser that can navigate can submit a form, which
routed it to execution approval instead of artefact approval.

## The scheduler

`fabric/scheduler.py` · `SCHEDULER.md`

Five queues. The one that carries the design is the split between the last two:

> `WAITING` resolves by itself. `BLOCKED` never will.

Merged, they produce a queue where half the entries are progressing and half are
dead and nobody can tell which by looking — so the operator either chases things
that were fine or ignores things that were stuck. They are separate queues, and
a test asserts they are not the same queue rather than asserting a happy path.

The order of the checks *is* the policy: blocked, then credential, then
placement, then budget, then waiting, then a chosen window, then the night
window, then ready. Asking "is there capacity" about work that cannot run at all
produces a queue full of things that look imminent.

Four decisions worth naming.

**UNKNOWN cost is neither free nor a wall — and the first version got this
wrong.** It reused the night-window threshold (`EXPENSIVE_UNITS = 50`) as the
affordability test for unpriced work, which blocked every unestimated mission on
the LIST plan (40 units) for ever. "Can we afford this estimate" and "should we
start something nobody priced" are different questions. Two thresholds now:
priced work is refused when its estimate exceeds what remains; unpriced work is
refused only when headroom is below `UNPRICED_NEEDS`, and the reason names the
missing estimate rather than a size. A test pins it against the real LIST
allowance rather than an abstract number.

**A missing credential is BLOCKED, not WAITING.** Nothing resolves it but a
person typing a key, and the reason names the Credential Centre — a reason that
does not say where to fix it is a status, not an action.

**Deferring is a decision, and it is enforced.** `service.defer()` records
`not_before` as an ordinary append-only event; the mission stays *queued*,
because it is still work somebody wants done. Then `claim()` refuses a mission
whose window has not arrived. Without that last part the worker — which takes
the oldest queued mission — would run the night job at eleven in the morning and
the deferral would be a suggestion.

**Oldest-first inside a priority.** Ordering by priority alone starves the
NORMAL mission that has been waiting since Tuesday behind a trickle of newer
NORMAL work.

Durability is shown across a real process boundary: a deferral written by the
test interpreter is read by a `subprocess` that never saw it — with a negative
control proving the same fresh process *would* have run the mission without the
deferral, so the test cannot pass against a scheduler that defers everything.

## The message protocol

`fabric/protocol.py` · `AGENT_PROTOCOL_AND_BUDGETS.md`

Two agents that can talk can talk forever.

**An agent addresses a capability, never an agent.** `needs=Capability.RESEARCH`,
not `to="researcher"`. This is what keeps "agents cannot recruit agents" true
while agents still collaborate: an agent that could name its correspondent could
build a private chain outside the registry — working relationships nobody
declared and no policy covers.

**The cap escalates; it does not truncate.** At the hop limit, the message limit
or the budget, the conversation goes to a person with the whole chain attached.
Silently returning the last message hands the caller a half-finished answer that
reads like a finished one, and the loop — invisible — runs again tomorrow. The
escalation is written *even when the message cap is already full*, because the
cap bounds work, not the record of why the work stopped.

**Cycles are caught by who is still waiting**, not by who has been asked before.
A second question to the same specialist, after the first was answered, is
ordinary work; a rule that called it a loop would block normal collaboration. A
failure counts as an answer, so a legitimate retry is not refused as a cycle.

`REFUSED` (a rule said no, and which) stays distinct from `FAILED` (something
broke). A caller that cannot tell them apart retries against a limit that will
refuse it every time.

## Budgets — and the mistake caught on the way

`fabric/budgets.py`

    TENANT   ⊃   MISSION   ⊃   AGENT   ⊃   CONVERSATION

Checked against **all**, committed to **all**. Checking only the tightest lets a
hundred conversations, each inside its own small budget, empty the tenant's;
checking only the widest lets one of them do it alone; committing scope by scope
leaves the tenant charged for a spend the conversation refused, and that
overcharge is invisible.

**The mistake:** the first version invented `budget.<tenant>` as the tenant
allowance. `credits/` already owns that question — a customer's plan, registered
on this same ledger by `CreditService.assign()`. Two answers to "what may this
customer spend", and the wrong one is always whichever the operator is not
looking at. `Scope.TENANT` now resolves to the credits resource, `policy()`
refuses to define a tenant allowance at all, and a test pins the delegation.

This is the same failure mode as the parallel-maps and second-registry problems
recorded earlier in this project, caught this time before it shipped.

`Unmetered` is deliberately not a `QuotaExhausted`: "you have no allowance
configured" and "your allowance is gone" have opposite remedies, and a caller
that confuses them waits for a window that is never going to reset.

## What is wired

`GET /api/missions/schedule` asks `CreditService.balance()` for the tenant's real
remaining units — `balance()`, not the raw ledger, because it also subtracts
units already reserved and not yet settled. A mission whose plan estimates more
than the tenant can afford is `BLOCKED` before it starts.

`usable_credentials()` asks the same question `resolve()` asks: is the status
outside `UNUSABLE`? A credential somebody typed and nothing verified is exactly
the case where the scheduler would dispatch work that fails at the provider. A
sealed vault yields the **empty set** — not knowing which keys work is not the
same as knowing they all do.

New surfaces: `GET /api/missions/schedule`, `POST /api/missions/{id}/defer`
(requires `EXECUTE` — changing when work runs is an execution decision), and a
**Schedule** page in the console drawing the five queues apart.

## What is not built, stated rather than implied

- **Nothing calls `reserve()` from the worker.** The budget layer is complete
  and tested and the scheduler consults the tenant balance, but per-mission,
  per-agent and per-conversation allowances are not charged at execution time.
- **`Conversation` is not persisted.** It is designed to fold — frozen,
  counters derived from the messages — but no event kind writes it.
- **Provider rate limits** are not a scheduling or protocol input.
- **Multi-worker capacity is not discovered.** `concurrency` is supplied by the
  caller, and nothing counts live workers.
- **CLI/coding-agent backend** was `not ready` in the registry at this point
  because Qevik had no sandbox. Step 6, below, changed that: the host has one,
  and `cli-implementer` is now blocked on a credential instead. The claim and
  sandbox blockers named here were both resolved later in this same session —
  see the step 5 and step 6 sections.

## Step 5 — and a blocker that had already lifted

`MASTER_STATE.md` carried `PostgresClaims` as `PENDING_INFRASTRUCTURE`: "needs a
database". Checking the host rather than trusting the note found **PostgreSQL
18.6 already running on qevik-core-01**, with a `qevik_test` database and
psycopg 3.3.4 in the deployment venv. The blocker had lifted and nobody had
noticed — which is its own lesson about status notes that are never re-tested.

`infra/verify_postgres_claims.py` raced **eight OS processes**, each with its own
connection, spinning until a shared start instant so they reach the `SELECT`
together. A staggered start would let the first finish before the second began
and the run would pass against an implementation with no locking at all.
Exactly one claimed the mission. 13 checks, 0 failures — output recorded in
`reports/postgres_claims_verification.txt`.

### The bug it found

`SELECT … FOR UPDATE SKIP LOCKED` holds its lock until the **transaction** ends.
On an autocommit connection that is the semicolon — so the lock is released
before the `UPDATE` that records the claim, and two workers claim one mission
**with no error at all**. The exact failure mode the module exists to prevent,
one keyword argument away. `PostgresClaims.__init__` now refuses it.

That is why "written correctly" and "somebody watched it run" are two fields.
The algorithm was right; the constructor was not.

### What changed, and what did not

`verified()` now accepts `PostgresClaims`, and `DEMONSTRATED_BY` names the run,
the host, the database version and the report so a reader can check rather than
take it on trust. A test asserts the report exists and says it passed — a
pointer that outlives its file is a citation, not evidence.

The **deployment is still single-worker**. `create_app` builds `PostgresClaims`
only when `QEVIK_CLAIMS_DSN` is set; it is not set, and `/api/health` says
`SINGLE_WORKER_ONLY`. A configured-but-unreachable database falls back to
`LocalClaims` and logs the loss of safety — refusing to start would take the
control plane down over a capability only the worker needs, and falling back
*silently* would leave the operator believing in safety they do not have.

Still to do before two workers can run: set the DSN, and call `register()` from
the mission worker so a mission has a row to race for.

## Step 6 — the sandbox, and a second blocker that had already lifted

Same pattern, same lesson. `MASTER_STATE.md` carried the coding-agent sandbox as
`PENDING_INFRASTRUCTURE`: "needs a host". The host had **bubblewrap 0.11.1** and
unprivileged user namespaces already enabled.

Two status notes in a row that were true when written and had quietly stopped
being true. Worth saying plainly: a blocker nobody re-tests is indistinguishable
from a blocker that is still real, and both of them stop work.

### What the sandbox enforces

A CLI coding agent is not a model call — it is a process with its own tool loop.
A git worktree is version control, not containment: a process inside one can
still read `~/.ssh` and POST anywhere. So `fabric/sandbox.py` gives it one
writable directory, no network unless the work says it needs one, an environment
**allow-list**, and a wall clock.

`NoSandbox` refuses to run rather than executing unconfined. A passthrough would
make "the agent cannot read `~/.ssh`" fail loudly on a machine with a sandbox and
pass silently on one without — precisely backwards. An AST test asserts there is
exactly one `subprocess.run` in the module.

### 16 real escape attempts, 0 failures

`infra/verify_sandbox.py` on qevik-core-01. Each check runs a real command inside
the sandbox and asserts it could not do the thing, **paired with a control that
does the same thing outside and asserts it worked** — a check that passes because
the command was broken proves nothing. Output in
`reports/sandbox_verification.txt`.

Three findings, all from running it rather than reading it:

- `/root` is not merely unreadable inside — it does not exist. Stronger than the
  check expected; the check was reframed to accept either form of containment
  rather than one error message.
- **With the network on, a process still could not resolve `localhost`.** The
  root is an empty tmpfs and `/etc/resolv.conf` was never bound, so an agent that
  asked for the network would have got a confusing DNS failure and concluded the
  host was broken. `RESOLVER_PATHS` is now bound read-only when, and only when,
  the network is on.
- In the harness: `ls … | head` reports *head's* exit code, always 0, so an
  exit-code assertion behind a pipe is unfalsifiable.

A fourth came from the unit tests: `Bubblewrap(binary="/does/not/exist")` was
accepted, moving the failure from construction — where it says "there is no
sandbox here" — to the first run, where it looks like the agent's command
failing.

### Readiness became a property of the host

`Agent.ready` is now **derived** from a structured `Agent.blocked_by` rather than
stored beside it. Two fields are two answers to "can this run", and they drift
the first time somebody clears a blocker and forgets the flag.

The first version of `on_a_host_with_a_sandbox()` lifted every CLI agent, which
was wrong: `browser` waits on a browser worker, and `administrator` needs a
per-action approval policy as well as a sandbox — a shell on a host is not
reversible, and containing it does not make it so. `Need` makes each blocker a
value, so a sandbox lifts exactly `Need.SANDBOX`. Matching on the prose in
`why_not_ready` would have broken the first time somebody improved the wording.

### Still not done

Nothing runs a coding agent through the sandbox yet. `Bubblewrap.run()` executes
an arbitrary command under isolation; wiring it to the worker's agent invocation
is the remaining step. `cli-implementer` is now blocked on `CREDENTIAL` rather
than on the sandbox — a different blocker, and a smaller one.

## Step 7 — the tool contract, and two more errors it found

Section Q of the fabric architecture lists browser, email, server, git, CRM,
marketplace and social agents. The operator's standing instruction is that those
**features** are not to be started. What was missing is the thing underneath
them, and that is what step 7 built.

`Agent.tools` was a tuple of free-form strings. Nothing checked a name existed,
nothing said what a tool could do, and nothing connected it to the isolation the
agent would run under. Two lists kept in step by hand — the exact drift the
standing rule exists to prevent.

Writing the table down found two real errors in a registry that had passed every
test in the suite.

**`shell` meant two different things.** `cli-implementer` ran a shell in a
sandboxed worktree and declared REVERSIBLE; `administrator` ran a shell on a
live host and declared IRREVERSIBLE. Both were right about their own case, and
both named the same tool. They are now `shell` and `host-shell`.

**`browser` understated itself.** It declared REVERSIBLE. A browser that can
navigate can also submit a form, buy something, or send a message — nothing about
"browse" is reversible once a button is clicked. That single wrong word routed it
to *execution* approval instead of *artefact* approval.

Neither was findable by reading the agent records; both fell out of putting the
blast radius where it belongs — on the tool — and asserting the two agree.

A third, from the same file: `Agent(..., ready=False)` had become silently
acceptable once `ready` turned into a derived property, so a record written the
old way would report itself **ready** while its author believed they had said
the opposite. `extra="forbid"` now refuses it. Same failure as the `Prose(source=…)`
kwarg this project swallowed once before.

### What is enforced now

- A tool name no record defines fails the build.
- A tool nothing reaches fails the build — drift in both directions.
- No agent may declare a milder blast than its tools allow.
- Anything marked `contained_by_sandbox` must be local and reversible: calling a
  sent email contained because the process sat in a namespace would be the most
  dangerous kind of wrong.
- `needs_network(agent)` feeds `sandbox.Isolation`, so an agent whose work is
  local runs with the network unshared **by the kernel**, not by a line in a
  prompt.
- An agent holding a tool whose credential it never lists fails the build, with
  a negative control proving the check can actually fire.

### What was deliberately not built

No CRM, marketplace, social, media or email-sending **feature**. What exists is
the contract each of them will have to satisfy. Nothing dispatches through a
tool yet — that wiring is the same missing piece named in `SANDBOX.md`.
