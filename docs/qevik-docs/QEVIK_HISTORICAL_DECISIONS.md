## 1. Product Identity

Qevik was intended to be an **autonomous, evidence-driven
business-production and digital-execution system**.

It is not merely: - a chatbot - a website generator - a coding
assistant - an automation tool

The core conceptual loop is:

``` text
Research
→ Evidence
→ Opportunity / Requirement
→ Recommendation / Plan
→ Approval where required
→ Mission
→ Recipe
→ Agent
→ Tool
→ Worker
→ Artefact / Result
→ QA / Review
→ Approval where required
→ Publication / External Action
→ Measurement
→ Re-evaluation
```

## 6. Manual WhatsApp Validation

The historical project deliberately preserved a human-in-the-loop
outreach mode.

The intended distinction is:

``` text
APPROVED_FOR_MANUAL_SEND
→ human/operator personally sends
→ customer response
→ learn:
   - interest
   - rejection
   - objections
   - pricing reaction
   - offer clarity
   - perceived value
   - customer needs
```

This is not automated delivery authorization.

The five existing manually approved WhatsApp drafts are
historical/manual validation artifacts and must not be silently migrated
into automated sending.

Do not automate WhatsApp unless a later explicit product decision
authorizes it.

## 7. Website Factory

Websites are intended to be genuinely functional, not merely generated
HTML.

Production verification includes, where applicable: - HTTP/page load -
runtime errors - routes - responsive rendering - screenshots - links -
forms - API connectivity - authentication - performance - deployment -
smoke tests

A website must not claim functionality it does not actually provide.

Booking/appointment experiences must not imply confirmation unless
confirmation actually occurs.

## 16. Fabric / Workers


### Automated path

``` text

→ authorized_automated_at
→ explicit SEND
→ OutreachService
→ suppression
→ cooldown
→ duplicate protection
→ channel adapter
→ EmailChannel
→ SMTP

```

## 27. Important Outreach Fingerprint Decision

For the Opportunity/Proposal pipeline:

``` text
Proposal.fingerprint
```

is the canonical fingerprint and represents:

``` text
subject
+ body
+ offer
+ price
+ findings_fingerprint
+ claims
```

The Mission pipeline is allowed to have its own canonical fingerprint
derived from Mission-owned authoritative evidence and the exact composed
artifact.

The commonality is the authorization/guard/send layer, not forcing every
upstream pipeline to manufacture a Proposal.

Do not synthesize Findings or placeholder Proposals merely to reuse
`Proposal.fingerprint`.
